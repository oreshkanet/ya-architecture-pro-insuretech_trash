# Проектирование технологической архитектуры

На основе предоставленных требований и текущей архитектуры, ниже приведено описание целевой технологической архитектуры, отвечающей требованиям бизнеса по масштабируемости, отказоустойчивости, доступности (99,9%), RTO ≤ 45 мин, RPO ≤ 15 мин и географически равномерной задержке.

## Стратегия масштабирования и отказоустойчивости

1. **Микросервисы**
   
    Горизонтальное масштабирование стоит рассмотреть для всех микросервисов (`core-app`, `client-info`, `ins-product-aggregator`, `ins-comp-settlement`). С учётом того, что все микросервисы уже размещены в кластере Kubernetes в качестве инструмента автомасштабирования можно использовать Horizontal Pod Autoscaler (HPA). Он позволяет не только обеспечивать нужный уровень отказоустойчивости за счёт параллельной работы нескольких экземпляров приложения, но и автоматически добавлять новые при всплесках нагрузки.

    Если некоторые микросервисы не поддерживают горизонтального масштабирования, то можно рассмотреть вертикальное масштабирование как временное решение. Но стоит адаптировать все микросервисы и реализовать такую возможность.

2. **База данных**
   
    Для базы данных можно применять вертикальное масштабирование, но так же временно. Основной путь - разворачивание нескольких узлов СУБД, настройка репликации и шардирования при необходимости, организация надёжной системы резервного копирования и восстановления данных.

3. **Распределение по зонам**

    Архитектуру стоит эволюционировать от «один кластер + одна БД» к мультирегиональной схеме: несколько региональных Kubernetes‑кластеров с геораспределённой маршрутизацией и отказоустойчивой PostgreSQL с репликацией и регулярными бэкапами, что позволяет уложиться в RTO 45 мин, RPO 15 мин и 99,9% доступности. 

4. **CDN**

    Для обеспечения одинакового времени загрузки из всех регионов РФ — использовать CDN для фронтенда и статики, а весь пользовательский трафик маршрутизировать к ближайшему региону с использованием GSLB.

## Конфигурация развёртывания приложения в Kubernetes

Целевая инфраструктурная схема:

- Не менее двух региональных кластеров Kubernetes в разных зонах. Кроме того, можно рассмотреть разворачивание каждого кластера в нескольких зонах доступности (AZ) для HA на уровне региона.
- GSLB для маршрутизации клиентов в ближайший рабочий регион, плюс health‑checks для автоматического переключения трафика при падении региона.
- CI/CD и GitOps для идентичного развёртывания `core-app`, `client-info`, `ins-product-aggregator`, `ins-comp-settlement` и фронтенда во все кластеры с минимальными региональными отличиями в конфигурации.

## Балансировка нагрузки

GSLB (Global Server Load Balancer):

- Используется глобальный балансировщик (GSLB), который направляет пользователя к ближайшей точке входа (ЦОД).
- Внутри ЦОД — L7-балансировщик (например, Yandex Application Load Balancer или NGINX Ingress Controller с ExternalIP в обеих AZ).
- Health checks на уровне балансировщика: /healthz endpoint у каждого сервиса (HTTP 200 OK).
- На уровне Kubernetes readiness/liveness probes для каждого Pod’а.

Это позволит балансировщикам автоматически исключать нездоровые AZ или ноды.

При этом Фронтенд и статика выносятся на CDN с edge‑узлами по РФ и кешированием статики (JS/CSS/иконки/изображения), что минимизирует время ответа и делает загрузку страниц одинаковой при любых часовых поясах.
​​
Однако для внутренних вызовов между сервисами нужно минимизировать запросы к сервисам в другом регионе, чтобы не добавлять межрегиональную латентность.

## Фейловер-стратегия

Сервисы и паттерны развертывания:
- `core-app` и `client-info`:
  - работают в режиме active‑active по регионам, обслуживая запросы «своих» клиентов через ближайший кластер.
  - все изменения клиентских данных и заявок идут в основной регион БД, чтения по возможности выполняются из локальной реплики (read‑replica) в каждом регионе.

- `ins-product-aggregator`:
  - разворачивается в каждом регионе, интеграции с 5 страховыми компаниями лучше дублировать (по крайней мере для чтения тарифов и котировок), чтобы уменьшить межрегиональную латентность.
​
- `ins-comp-settlement`:
  - может работать в режиме active‑standby (один активный экземпляр на систему) с возможностью переключения в другой регион, поскольку это раз в месяц и не критично к минимальным задержкам.

Резервирование и аварийное переключение:

- Регулярные бэкапы БД (snapshots + WAL‑архивы) с хранением в отдельном регион/облаке и регулярными тренировками восстановления для проверки реального RTO.
​
- План DR - чёткая описание кто и как переводит трафик на резервный регион, как переключается PostgreSQL (promote standby), как проверяется целостность данных и запускаются приложения.
​
- Мониторинг и алертинг по регионам (Prometheus/Grafana/Loki и т. п.) с чёткими SLO по доступности 99,9% и автоматическими проверками основных пользовательских сценариев.

## Конфигурация базы данных

PostgreSQL разворачивается в виде отказоустойчивого кластера (Patroni/репликация) с:

- синхронной репликой внутри региона (multi‑AZ) для доступности 99,9% и защиты от падения одной зоны;

- асинхронной репликацией в резервный регион для DR — это позволяет обеспечить RPO 15 минут, при условии частых WAL‑архивов и тестируемой процедуры восстановления.
​
- Объём 50 GB позволяет комфортно использовать репликацию и частые инкрементальные бэкапы, что укладывается в заданные RTO/RPO при отработанной процедуре переключения.


## Шардирование БД

Текущий объём данных — 50 ГБ, прогнозируемый рост — значительный, но не экстремальный. Шардирование НЕ требуется на текущем этапе. Вместо этого — вертикальное масштабирование БД + использование Read-реплики для тяжёлых запросов.
